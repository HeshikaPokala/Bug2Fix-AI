# Demo / eval set: 30 bugs across 6 categories

This folder is a self-contained eval set proving the pipeline generalizes, and
measuring — with a large enough sample to actually mean something — exactly
where the deterministic fallback ends and the Ollama-assisted reasoning step
(`phi4-mini`, local, no API key) takes over. It also documents a full
diagnose → isolate → fix → verify cycle: a systematic failure category was
found, cross-model comparison ruled out "model is too small/not code-savvy"
as the cause, the actual cause (positional JSON argument binding) was fixed,
and the fix was verified to close the gap in two different models.

Bugs 1-9 are hand-written (the original demo). Bugs 10-30 are generated from
[`scripts/bug_catalog.py`](../scripts/bug_catalog.py) by
[`scripts/generate_demo_bugs.py`](../scripts/generate_demo_bugs.py) — a data
file of `{module, function, source, error_type, title, ...}` entries, not 21
hand-written file pairs, so the set is easy to audit, extend, or regenerate.
`results/eval_summary.md` / `.json` are auto-generated by
[`scripts/run_eval_suite.py`](../scripts/run_eval_suite.py) — re-run it after
any change rather than hand-editing the results.

## Model(s) used

Primary results are from the **plain base Phi-4-mini** — pulled as
`phi4-mini:latest`, resolving at the time of these eval runs to digest
`78fad5d182a7` (`phi3` architecture, 3.8B parameters, `Q4_K_M` quantization,
131072 context length), run locally via Ollama. Not the `phi4mini-lora-ckpt500`
checkpoint fine-tuned for the ClinicalExtract project — deliberately: that
checkpoint was fine-tuned for a different task (clinical JSON extraction),
so there's no reason to expect it would transfer here, and it could plausibly
do worse by having drifted from general instruction-following.

The comparison model is **`qwen2.5-coder:7b`** (Alibaba's Qwen2.5-Coder,
`qwen2` architecture, 7.6B parameters — 2x phi4-mini's size *and* specifically
trained on code — digest `dae161e27b0e`, `Q4_K_M`). See "Cross-model
comparison" below.

The `:latest` tag is a moving target; treat the digests above (not the tags)
as what these specific numbers measure. `app/tools/llm_tools.py` reads the
model from `OLLAMA_MODEL` (default `phi4-mini:latest`) and the host from
`OLLAMA_HOST`.

```bash
python3 scripts/generate_demo_bugs.py         # regenerate bugs 10-30 from the catalog
python3 scripts/run_eval_suite.py             # both modes, ~3-5 min with Ollama
python3 scripts/run_eval_suite.py --skip-llm  # deterministic only, seconds
OLLAMA_MODEL="qwen2.5-coder:7b" python3 scripts/run_eval_suite.py  # run against a different model
```

## The 6 categories

| Category | Count | Shape | Fallback (6 fixed guesses) alone |
|---|---|---|---|
| `fallback` | 12 | crashes on `None` / `[]` / `0` / `""` / `{}` | **Solves all 12** |
| `llm_dict_key` | 4 | needs a real, correctly-typed dict + a specific missing string key | **Can't** — every repeated-value guess produces `TypeError`, never `KeyError` |
| `llm_threshold` | 4 | needs a number past a threshold well outside the 6 fixed values | **Can't** |
| `llm_relational` | 4 | needs two coordinated numbers where `a > b` (optionally `a > b + k`) | **Can't** — no repeated single value satisfies a strict inequality |
| `llm_wraparound` | 2 | needs an int outside a list's valid range, accounting for Python's negative-index wraparound (`-1` alone doesn't trigger it) | **Can't** |
| `llm_string_length` | 2 | needs a string longer than a threshold | **Can't** — empty string is always too short |
| **Total** | **30** | | **12/30 solvable without any LLM** |

## The finding: positional JSON args vs. named JSON args

**Original design** (all 3 initial `phi4-mini` runs, 2 initial `qwen2.5-coder`
runs): asked the model for `{"args": [value1, value2, ...]}` — a positional
list. Result: **24/30 (80%)**, with a clean, total, reproducible **0/4** on
every `llm_dict_key` bug (needs a correctly-typed dict in one argument slot
and a string in another), identical across both models, across 5 independent
runs (20 consistent data points). The model kept putting a string where the
dict belonged — e.g. `{"args": ["discontinued_sku", ""]}` for
`get_line_item_price(catalog: dict, sku: str)`.

**Hypothesis**: this isn't a reasoning failure (both models correctly explain
each bug's root cause in English, and solve every single-typed-argument bug
perfectly) — it's a *format* failure. A positional array gives the model no
explicit place to state "this value is for the `catalog` parameter, which is
a dict" — it has to silently track position-to-type binding across two
different types from one signature shown once, and it doesn't reliably do
that.

**Fix**: changed the prompt (and Ollama's `format: "json"` constraint) to ask
for a JSON **object keyed by parameter name** instead —
`{"args": {"catalog": {...}, "sku": "..."}}` — with each parameter's name and
declared type spelled out explicitly beforehand. The response is then
validated (every parameter name must be present) and converted to the
ordered positional list the actual Python call still needs — the runtime
probe script itself didn't change at all, only how the model is asked to
answer. See `_extract_params` / `_validate_named_args` /
`_llm_propose_args` in [`app/agents/reproduction.py`](../app/agents/reproduction.py).

**Result, verified with 2 full runs per model:**

| | Positional args (before) | Named args (after) |
|---|---|---|
| `phi4-mini` | 24/30, `llm_dict_key` 0/4 | **29/30**, `llm_dict_key` **4/4** |
| `qwen2.5-coder:7b` | 24/30, `llm_dict_key` 0/4 | **29/30**, `llm_dict_key` **4/4** |

The fix closed the exact gap it targeted, in both models, immediately (every
`llm_dict_key` bug now solves on the first attempt, no retry needed) — strong
confirmation that the original 0/4 really was an interface problem, not a
capability ceiling. First real example, printed by the pipeline itself:
```
--- trying input=llm attempt 1 ([{'SKU123': 19.99, 'SKU456': 29.99, 'SKU789': 39.99}, 'SKU000']) ---
KeyError: 'SKU000'
REPRO_MATCH input=llm attempt 1 error=KeyError
```

**The one bug that didn't move**: `bug5` (`wallet.withdraw`, needs
`amount > balance + 50`, an *arithmetic-offset* relational condition) still
fails for `phi4-mini` (both attempts proposed the exact same numbers even
after a retry) — expected, since named arguments fix type-binding, not
arithmetic reasoning, a different failure mode entirely. Interestingly,
**`qwen2.5-coder` solved bug5** with named args (2 attempts, the retry
worked) — the first place the two models diverge in a way that isn't a
coin-flip. In exchange, `qwen2.5-coder` now fails `bug29`
(`llm_string_length`) where it succeeded before, and `phi4-mini` doesn't.
Both models land at 29/30, just with a different single miss each — real,
stable model-specific variance at this point, not a shared systematic
category the way `llm_dict_key` was.

## What actually predicts success now

- **`llm_threshold` (4/4) and `llm_wraparound` (2/2) — 100%, both models,
  both before and after the fix.** These never needed the named-args change;
  a single-typed numeric guess was never ambiguous.
- **`llm_dict_key` (4/4) — 100%, both models, only *after* the fix** (was
  0/4 before). This is the category the named-args change actually targeted
  and closed.
- **`llm_relational`, direct comparison (3/3) — 100%, both models.**
  `requested_seats > available_seats`-style bugs, no offset arithmetic
  needed.
- **`llm_relational` with an arithmetic offset (bug 5) — model-dependent.**
  `phi4-mini` still can't do the `+50` arithmetic; `qwen2.5-coder` can. This
  is the one place raw capability (not format) plausibly does matter.
- **`llm_string_length` (1/2, both models, but a different bug each) —
  genuinely mixed**, not systematic in either direction.

## Results summary (`phi4-mini`, named-args, 3 full runs — 29/30 all three)

- **Diagnosis correct: 30/30**, every run — pure log parsing, doesn't depend on the LLM.
- **Repro confirmed, deterministic fallback only: 12/30.**
- **Repro confirmed, with Ollama (named-args): 29/30 (96.7%).**
- **In plain terms: 12/30 succeed either way, 17/30 succeed *only* because of Ollama, 1/30 (`bug5`) fails even with Ollama's help.** 12 + 17 + 1 = 30.
- **Zero bugs flipped across all three runs.**

## Why 29/30 — not 30/30 — is still the right kind of result

`bug5` still doesn't get a confirmed repro from `phi4-mini`, and that's
reported honestly rather than hidden: the pipeline correctly diagnosed the
function, file, and exception type, correctly explained the root cause in
English, and then — unable to prove the repro — downgraded confidence to
0.74 and let the reviewer flag it, instead of pretending it worked. The
original (pre-generalization) version of this project "succeeded" on 100% of
inputs only because its reproduction step never actually tested anything.
29/30 with one honestly-reported, well-understood miss is a stronger result
than a suspicious 30/30 would be.

## What this demonstrates

- The diagnosis layer (log parsing) is fully general — 100% correct across
  30 unrelated bugs across 20 different files.
- A systematic failure category (`llm_dict_key`, 0/4) was found, confirmed
  with a cross-model comparison to rule out "model too small" or "model
  doesn't know code" as the explanation, traced to a specific mechanism
  (positional JSON argument binding), fixed, and the fix was verified to
  close the gap in *both* models independently — a full diagnose-and-fix
  cycle with real before/after numbers, not just a single measurement.
- The one remaining model-specific gap (`bug5` for `phi4-mini`, arithmetic-
  offset reasoning) is named precisely rather than lumped in with the fixed
  category, so it's clear what's actually still a capability limit versus
  what was a solvable interface problem.
- The eval harness makes all of this repeatable: `python3
  scripts/run_eval_suite.py` reproduces the 12/30 vs 29/30 split, and
  swapping `OLLAMA_MODEL` reproduces the cross-model numbers, rather than
  any of this being a one-off, unverifiable claim.
